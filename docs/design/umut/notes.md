# Design Notes - Database and Data Import (T4)

## Database Design (database.drawio / database.png)

This diagram shows the tables and relationships of the local embedded database used by `DataRepository` to store all application data on the user's computer without a network connection (FR 27, NFR 10). The main tables follow the classes in `class-list.md` and store `Course`, `Student`, `Classroom`, `ExamPeriod`, and `TimeSlot`, along with student enrolments, classroom features, and unavailable time slots (FR 1, FR 2, FR 4, FR 5, FR 9-13). The `exam_period` table also stores the user settings needed for the scheduling rules, such as the default exam duration, the 30-minute classroom changeover time, and the invigilator limits (FR 5, FR 36, FR 43, FR 47). The generated schedule is stored in `exam_schedule`, `scheduled_exam`, and `classroom_allocation`, where each course gets one time slot and one or more classrooms, and `allocation_student` records which classroom each student is placed in (FR 7, FR 28, FR 33, FR 34). Invigilators are kept in separate optional tables (`invigilator`, `invigilator_unavailability`, and `allocation_invigilator`), so a valid schedule can still be created and saved even if no invigilator list is imported (FR 14-16, FR 43-49). When the input data changes, the previous schedule is not deleted; instead, its status in `exam_schedule` is set to outdated so it can still be used if the user wants the new schedule to stay close to the old one (FR 26, FR 42).

## Import Sequence Diagram (import-sequence.drawio / import-sequence.png)

This diagram shows how `DataImporter`, `DataRepository`, and `ScheduleUpdater` work together when the Student Affairs staff imports or re-imports a plain-text input file through the user interface (FR 1, FR 3, FR 6, FR 14). First, `DataImporter` reads the selected file, skips title lines, empty lines, and extra spaces, and checks the records against the current data loaded by `DataRepository` (FR 23, FR 24). If any error is found, `DataImporter` stops the import without changing the database and returns the file name, line number, and cause of each problem (FR 24). If the file is valid, `DataImporter` counts how many records will be added, changed, and removed, and sends this summary to the user interface to ask for confirmation (FR 25). Only after the user confirms does `DataRepository` save the new data safely so that closing the application during an import cannot damage existing records (FR 3, FR 27, NFR 9). After saving, `ScheduleUpdater` checks whether an `ExamSchedule` already exists and marks it as outdated so the user knows the schedule may no longer match the updated data (FR 26).
